# Map renderer parity: TTC and GO/UP

TTC and GO/UP must look and behave the same over their SVG maps: same overlay vocabulary, same gesture handling, same stability. Both render through one engine, `components/system-map/SystemMap.tsx` ([plan 10](refactor-plan/10-one-map-engine.md) phase 4), which owns loading the artwork and rasters, the entrance and camera, the plane stack, station targets and names, taps, hover, train markers, overlap badges and the chooser. A map is a definition (`components/system-map/ttc-system-map.ts`, `regional-system-map.ts`): its manifest (`app/map-manifests.ts`: view box, stage, overlay unit, framing, station hit padding, station-name padding and cutout, compass, attribution, raster planes), prepared geometry, how to prepare its SVG, and its network's content adapter (`app/ttc-map-content.ts` with artwork obstacles in `ttc-map-obstacles.ts`; `app/regional-map-content.ts` over `app/regional-*.ts`). `InteractiveTtcMap.tsx` and `InteractiveRegionalMap.tsx` only pair the engine with a definition. Every map has the same elements: its root (`.system-map`, named by `data-system-map="ttc|regional"`, where the camera writes its motion flags), its viewport (`.system-map-viewport`) and its camera stage (`.map-stage`). Styles and tests address one map with `[data-system-map=…]`; per-map CSS is artwork theming only. Most GO/UP-only flicker came from drawing the same overlays twice, so both maps now draw every live overlay with one shared React layer, `components/map-overlays/` ([plan](refactor-plan/08-unified-map-overlays.md)). What a map draws is one `MapContent` (`app/map-content.ts`, [plan 10](refactor-plan/10-one-map-engine.md) phase 3), built from dashboard data by the network's content adapter: line alerts, the selected alert's emphasis, station alerts and direction glyphs, the commute preview, outline paths, and overlap badge inputs with what badges keep clear of. Network differences live only in the adapters. Both maps place badges from it with `placeMapOverlapBadges`, keep unchanged items' objects across rebuilds (`reuseMapContent`), and draw train markers with one layer (`map-overlays/TrainMarkerLayer.tsx`) and the map's `MapTrainMarkerPlacement`.

**One overlay layer.** Both maps draw line alerts with `MapLineAlertLayer` (tubes, glyph lanes), `MapLineAlertSelection`, `MapLineAlertTargets`, `MapLineAlertHoverCopies` and `MapLineAlertHoverOutlines`; station alerts with `MapStationAlertRings` (ring target, beacon, core), `MapStationDirectionGlyphs` and `MapStationAlertForeground` (selection flash, hover priority ring); and commute previews with `MapCommutePreviewRoute` (route and endpoint dots, under station artwork) and `MapCommuteEndpointFlashes` (green flashes above it). TTC's design is canonical, sized by each map's `MapOverlayPlane.unit` (TTC 1; GO/UP 196 / 96); overlay CSS sizes multiply by `--map-overlay-unit`. Each network's adapter builds the overlay models from prepared geometry (GO/UP's in `app/regional-line-alerts.ts`, `app/regional-station-alerts.ts`, `app/regional-commute-preview.ts`), and the engine draws them in one plane stack (below). Station-only planned advisories are station alerts on both maps, chosen by the same `plannedAdvisoryStationImpacts` rule. A change to overlay drawing therefore lands on both maps at once.

Both maps run one camera, `hooks/usePanZoom.ts` ([plan 09](refactor-plan/09-system-map-engine.md) phase 1b): pan, wheel zoom, pinch, momentum, flights, fit framing, resize, persistence and the camera flags. The engine passes its viewport and stage, and the map's framing as data (`defaultFrame`: content bounds, phone zoom and centre station and side inset ratio from the manifest's `framing`, and the desktop toolbar and legend insets). One entrance places every map's camera once its artwork has loaded and its viewport has a size: while the shell defers the entrance, or (with no selection to frame) the rasters are still decoding, the camera waits at the fly-in start; the stage stays hidden until the camera is placed. Turning the phone refits the network on both maps. Selection framing, keyboard focus reveal, the desktop toolbar and legend insets and the toolbar's Center and zoom commands are one hook, `map-camera/useMapFraming.ts`: both maps find the selection's drawn elements by the shared overlay attributes (`app/map-selection-framing.ts`; alerts by their tubes, stations by `data-map-selected-station-id`), keep clear of the same panel edges, fit a selection at the same comfort ratio, frame again when an alert is reselected from a card, defer framing during a gesture, and fly back to the fitted map when a selection clears. An untouched camera refits on resize; one the rider moved, or a selection owns (`automaticRefitBlocked`), keeps its zoom and centre. The committed camera is a store (`map-camera/camera-store.ts`), not React state: a commit re-renders only the shared zoom slider and, while a chooser is open, the map that places it. Both maps also share hover (`map-hover-controller.ts`), the selection intro (`selection-intro.ts`), the pulse clock (`pulse-sync.ts`) and the badge and connector clearances around overlays (`overlay-obstacles.ts`). Neither map measures its SVG ([plan 09](refactor-plan/09-system-map-engine.md) phase 3): each map's geometry (station dots and shapes, segment anchors, route paths and guides, station-name boxes, badge obstacles) is prepared from the authored SVG at build time by `scripts/prepare-map-geometry.mjs` into `src/app/map-geometry/{ttc,regional}.json`, in root SVG coordinates, and read through `app/map-geometry-data.ts`, `app/ttc-map-geometry.ts` and `app/regional-map-geometry.ts`. `test:fast` fails when an SVG changes without `npm --prefix frontend run prepare:map-geometry`. Station-name boxes come from one rule (`stationLabelPolygon`), padded per map. Both maps place overlap badges and their connectors with one layout (`map-overlays/overlap-badge-layout.ts`, which returns its previous result for an equal request); each map supplies its badges, artwork obstacles and station dots. Both open the same alert chooser (`MapOverlapChooser`), placed from data by `map-overlays/useMapOverlapChooser.ts` through the map's stage transform (`meetStageTransform` from its manifest's view box and stage). What stays per map is its definition: content and framing data. Station targets, hover rings and the selected-station marker come from each map's artwork on both maps (`app/map-station-artwork.ts`, [plan 10](refactor-plan/10-one-map-engine.md) phase 1): a target has its dots' shape, grown by the manifest's `stationHitPadding` (TTC 6 units, 22 for touch; GO/UP 60), junctions keep their authored transform, and parts named with a `stationPartSuffixes` suffix (Spadina's two dots) are one station. Only stations the network has data for get a target; TTC places one its artwork lacks at its data position. Both maps take one tap path, `map-overlays/useMapTaps.ts` ([plan 10](refactor-plan/10-one-map-engine.md) phase 2): targets (stations, station names, line alerts, station alert rings) carry only their identity (`data-station-id`, `data-station-label-id`, `data-map-impact-*`) and select nothing themselves. The viewport resolves a press when it starts (on an alert, the alert the hover outline shows: the topmost station alert ring under the point, preferring any but the selected one) and selects it at release, unless the press moved the camera, stopped a glide or became a pinch; a release on open map clears the selection. Selection never waits for the synthesized click, which a camera commit or the details panel opening can drop and Android can retarget; that click is consumed before any child sees it. Enter, Space and assistive-technology clicks select the focused target.

**One plane stack** ([plan 09](refactor-plan/09-system-map-engine.md) phase 2). Both maps' stages stack the same planes, bottom to top: the background raster (and TTC's line-badge raster); the authored SVG, which paints only until the rasters are ready and then stays as a `visibility: hidden` geometry source that never takes the pointer; the overlay plane (alert tubes and glyphs, the commute route, selection emphasis, hover copies and station hover rings), under the station artwork; the foreground and label rasters; the top plane (the hovered station name, train markers, the compass); and the interaction plane (hover outlines, line alert targets, station targets, commute endpoint flashes, station alert rings, station-name targets, direction arrows, the selected station's marker and alert foreground, overlap badges). Every plane is React-owned and shares its map's view box; both maps mount their authored SVG whole, as artwork only (`app/map-artwork.ts` loads and prepares it once), and draw overlays in their root SVG coordinates. Nothing is injected into an authored SVG. Plane groups carry ids prefixed by the map's id (`ttc-dynamic-segment-layer`, `regional-dynamic-segment-layer`), unique while both maps are mounted. Station targets, hover rings, selection markers and station-name targets are one shared React layer, `components/MapStationLayers.tsx`; station hover is written by the shared `setMapStationHovered` (`map-overlays/station-hover.ts`). Hovering a station's dot, or focusing it on a fine-pointer device, rings the dot and lifts its name; hovering the name lifts the name without the ring. The lifted name is one component, `MapStationLabelHoverCopy`: the label texture's pixels inside the name's box (the manifest's `stationLabels.hoverPadding`), masked to its glyphs, which the label plane cuts out underneath. The glyphs come from the mounted artwork as the manifest's `stationLabels.cutout` says: TTC's authored label itself (`<use>`), GO/UP's prepared glyph copy (its names sit in a transformed layer, which `<use>` would drop). It shows only once the label font has loaded. Station targets are named `<Station> station details` on both maps and are the keyboard stops; station-name targets are pointer only on both (each station's target and hover ring is a memoized component, so a selection re-renders only the stations it changes).

## Baseline contract

1. **Overlay nodes live as long as their content.** Rebuild overlay DOM only when what it draws changes, and only for the alert that changed. A dashboard poll returns new arrays and fresh `updatedAt` stamps even when nothing changed, so compare drawn content, not object identity: both maps build their content on each render and keep each unchanged item's object across the rebuild (`reuseMapContent`), so a poll that only restamps the data draws nothing new. Alerts that leave the data fade out on both maps (`useRetainedMapItems`). When content does change, keyed React rendering re-renders only the changed alerts, on both maps. Selection and hover state applied in place does not count as a change. Anything that names an overlay (hover mask ids) must derive from the alert, not its position, or one new alert would change every other alert's markup.
2. **Presentation state never rebuilds overlays.** Reduced motion, page visibility, hover, selection, and gesture/zoom/camera flags are applied in place. A reduced-motion toggle or a brief visibility flip (fired on window `focus`/`pageshow`) must not delete overlay nodes. Hover is written to the DOM by the shared hover controller (rule 8), motion pauses through the shared pulse clock (rule 6), and station hover is written by `setMapStationHovered`; none of them rebuilds overlays.
3. **Alert overlays never move.** No alert overlay animates, on either map, on desktop or phone, at any number of alerts: glyphs rest along their lane (the shared `GlyphLane` in `map-overlays/GlyphLanes.tsx`), line alerts have no pulse, and station alerts draw a still core, beacon, and ring. One-way alerts show their direction through the glyphs' orientation. Selection feedback (the intro flash, then the breathing highlight) is the one animation an alert gets, and only while it is selected; both maps time the intro with `useMapSelectionIntro` (`map-overlays/selection-intro.ts`), keyed by `mapSelectionIntroKey`; `tests/map-motion-parity.test.mjs` guards this.
4. **Gestures use the same flags and timing.** The shared camera sets `data-map-gesture-active`, `data-map-zoom-active`, `data-map-camera-moving` and `data-map-pointer-dragging` on each map's root (`.system-map`) (GO/UP's former `data-regional-map-camera-moving` is gone), and share the simplification rules in `styles/map/base-map.css`. A direct drag follows the pointer with no transform easing. Wheel zoom and drag momentum come from one engine, `MapCameraMotion` (`components/map-camera/camera-motion.ts`), which both maps' handlers call ([plan 09](refactor-plan/09-system-map-engine.md) phase 1): it tells mouse-wheel notches from trackpad scrolls and pinches, eases each notch to its target around the pointer with a short transform transition (180 ms; per-frame scale writes from script made Chromium re-raster GO/UP's stage and overflow tile memory), applies scrolls and pinches directly, glides on after a drag released while moving, and commits the camera to React once, when the zoom has settled (100 ms after the last wheel event, once the ease has landed) or the glide has stopped. Zoom mode spans the ease and the gesture flag spans the glide; a press, a wheel or any camera command stops a glide where it is drawn, and a press that stops one selects nothing. Reduced motion applies notches at once and drops momentum. Both maps cancel the browser's own wheel action (page scroll, and page zoom on a trackpad pinch) with one native non-passive listener, `usePreventMapWheelDefault` (`components/map-wheel-events.ts`); React's `onWheel` is passive and cannot. Only targets take the pointer, and only in the interaction plane: alert tubes, glyphs and hover copies never do (`.asset-alert-path { pointer-events: none }`), and neither map's authored SVG does. (When GO/UP's targets lived inside its interactive authored SVG, a tube and its hover copy swallowed presses meant for the targets beneath.) Properties that gesture mode simplifies (`filter`, `stroke-width`) must snap back on release, never transition. Repeated overlay artwork (glyphs, icons) carries no `filter` at all: Chromium re-filters each one on every zoom frame, and the drop-shadow halo on planned-closure icons was most of GO/UP's dropped frames while zooming (frame p95 55 ms against 6 ms without). Animating a blur back repaints the whole map layer on every frame, even for invisible glows. When ending a gesture, both maps must fire no transitions.
5. **Hidden means not rendered.** Content that should not paint must stay out of the paint tree the way TTC's does. Hide authored source artwork with `visibility: hidden` on its children; never use `opacity: 0` on a container, because Chromium gives the invisible content its own GPU layers (about 55 for GO/UP's station-label source). Keep idle hover copies at `display: none` until hovered, and give a copy its `<use>` only while its alert is hovered (`setMapImpactHovered` adds and removes it): Chrome keeps every `<use>` clone in step with its alert even when hidden, and the camera flags restyle alerts on every gesture, which cost GO/UP about 4 ms of style work per flag change. On GO/UP, hidden copies and an `opacity: 0` label layer nearly doubled paint work and GPU layers. A map the rider cannot see (preparing or warming) is not re-rendered by the shell (`FrozenWhileHidden` in `NetworkMap.tsx`). No alert glows on hover or selection: hover draws the outline and a selection flashes.
6. **Remaining pulses share one clock.** The pulses that are left (a commute preview, a selected station) resynchronize to the shared 2.4-second cycle after the drawn overlays change or motion resumes, not on every gesture. Both maps run `useMapPulseSync` (`map-overlays/pulse-sync.ts`) over their whole map, so GO/UP's top-plane flashes join it too.
7. **The alert chooser rides the camera, and is placed only at rest.** Each map's camera writer passes every stage transform and transition to its `MapChooserFollower` (`components/map-chooser-follow.ts`). The card's portal `transform` then moves with its badge in lockstep, with no layout or React work. Placement runs only once the camera has committed and settled, never during a drag, pinch, or camera flight, and on both maps it is solved from data (`useMapOverlapChooser`: the badge's map position and outlines through the stage transform and the committed camera), never by measuring the page. A spot that is still valid is kept (`preferred` in `overlap-chooser-placement.ts`). A new spot is reached by a glide on the portal's separate `translate` property. A badge panned off screen keeps its card attached. The card keeps the badge's alerts uncovered as drawn: each line alert's hover outline and each station alert's hovered ring (the badge's `affectedOutlines` from the shared layout, mapped to the screen by `affectedOutlinesOnScreen`), on both maps. Geographic view follows MapLibre `move` events and re-places on `moveend`. The keep-out observer ignores map stages and the chooser itself, so camera frames do not trigger keep-out scans.
8. **One alert hovered is raised; a group is outlined.** Both maps run one hover controller, `installMapHoverController` (`components/map-overlays/map-hover-controller.ts`). It finds the hovered alert from the mouse's position: a station alert's ring first, else a line alert, which stays hovered while the pointer crosses a station drawn on top of it. Keyboard focus (`:focus-visible`) on an alert target hovers it too, on fine-pointer devices; the focus a click gives its target does not, so a pressed alert shows no hover outline once the cursor leaves it, including while its selection flashes. A press or wheel on the map ends the pointer hover on both maps: the alert hover, the station hover indicator, and the station-name label (a press on the label itself keeps it). Chooser and badge group previews stay, since the open chooser or hovered badge that owns them is still there; they end when it closes or loses hover. Hovering one alert, on the map or as a chooser row, raises that alert's hover copy above the others with its outline. Group previews (the open chooser with no row hovered, or a hovered or focused overlap badge) draw one outline around the union of the alerts (the shared `renderMapPreviewOutline`) and light their station rings, without raising any artwork, since several alerts cannot all be on top. Map and chooser hovers each own their raise, so ending one never clears the other. Hover is written straight to the DOM, so it shows before the next paint, and is reapplied when an alert's overlay remounts. The group outline stays visible during drags, without its glow. Masked outlines (group outlines and raised hover outlines) hide while the map changes scale (`data-map-zoom-active` or a camera flight) and return when it settles.
9. **Keyboard focus is never hidden.** A keyboard-focused map target under the sidebar, rail, or a sheet, or off screen, pans into view using the insets selection framing uses (`readMapOccludedInsets` in `map-camera/useMapFraming.ts`) and the shared `app/map-focus-reveal.ts`. Only `:focus-visible` focus inside the camera stage pans; chooser rows and pointer focus don't.
10. **Train markers move by one model.** Both backends send timed markers that use the same placement rules: at most 0.95 of the link while moving, 0.98 and `moving: false` when stopped at a station, and at least 0.12 once a train has left one. Both maps then advance them every second (`useAdvancedTrainMarkers`) and animate them along the track with the shared `train-markers.ts` motion. TTC's feed restates predictions as held countdowns that slide later with the clock, so its service keeps the earliest prediction for each train's next station (`GtfsRtSubwayTrainMarkerService`). GO/UP times each link from the trip's departure, else the timetable (`MetrolinxVehiclePositionClient`).
11. **Badge connectors cross only open space.** Both maps place badges and connectors with `layoutMapOverlapBadges`, passing the same kinds of artwork: station names (GO/UP also connection labels and line-name badges), every other overlap badge, station dots, and transit line strokes. The straight line never enters them, except right where it meets its own overlay. Its landing point moves along the overlay within `CONNECTOR_DETOUR_RATIO` of the shortest line, or the shortest plus `CONNECTOR_DETOUR_BADGE_HEIGHTS` badge heights. Badge placement passes the same check to `placeOverlapBadges` (`connector`): a spot whose line is blocked is passed over for the next clear spot, an aligned row is dropped if it leaves a member without a line, and each placed line is reserved so later badges keep off it. Only when no nearby spot has a clear line is a badge left without one. The end dot sits just outside the outline where the line actually crosses it, so a slanted line steps out by the half-width over the crossing angle. `BADGE_FEATURE_GAPS.alertOverlay` (28) leaves room for that dot plus a short line; the placement grid can eat at most half of its 10-unit clearance, so a badge at its closest spot is still well past the connector minimum length (12) and gets a line. Alert clearances come from the shared overlay sizes in `map-overlays/overlay-obstacles.ts`, at each map's overlay unit and badge scale (GO/UP draws badges at twice TTC's size): a line alert is an obstacle out to its hover outline (`MAP_HOVER_OUTLINE_WIDTHS.outer`) plus the `alertOverlay` gap, a station alert is a circle out to its whole drawing (`stationAlertAnchorReach`, beacon included) plus the same gap, and connectors end on the line alert's hover outline or the station alert's hovered ring (ring radius plus `STATION_ALERT_RING_STROKE_HALF_WIDTH`, or a pill's outline). Connectors keep `CONNECTOR_STATION_CLEARANCE` from the ring any station would draw. Badges keep the wide `BADGE_FEATURE_GAPS.transitLine` gap only from unalerted track: both maps pass their line obstacles through `withoutAlertedStretches`, so a stretch under an alert overlay keeps the overlay's tighter `alertOverlay` gap and badges can tuck into the nooks beside it.
12. **Station alerts are one component.** `components/map-overlays/StationAlertOverlays.tsx` draws every station alert, of every kind, on both maps and on desktop and mobile, from the model in `station-alert-model.ts`: an idle ring that is also the alert's pointer and keyboard target, a shaded beacon, and a still core over the dot, then one direction arrow per alerted dot, then the selected alert's flash and each alert's hover priority ring. Colours are TTC's (`stationAlertColor`): a red core and gold ring for a suspension or speed zone, amber for a delay, blue for a planned advisory. `stationImpactBeaconSize` (`components/station-impact-beacon.ts`) sizes the beacon at 2.2 core radii, or smaller when a neighbouring station dot is closer; two alerted dots close together, such as Spadina's platforms or a GO/UP pair, each get a full circle of half the space between them. Each map's adapter sizes the anchors: TTC's core is 26 units (48 at large stations), its ring 38 (56); GO/UP takes TTC's ratios of each dot's own radius (core 26/32, ring 38/26 of the core, arrow badge 24/32), since its dots vary. GO/UP's pill-shaped hub (Union) is an anchor shape of the same component: its filled outline marks the alert, with an invisible target band around it and no ring or beacon. The rings sit above station targets on both maps (TTC's interaction plane, GO/UP's top plane), and the beacon, core, and ring stay visible while the map moves. Metrolinx alerts carry no direction field, so a GO/UP arrow appears only when the backend names a trip's destination ("Towards Union Station"); `station-impact-direction.ts` points it towards or away from Union from the alerted station's place on the line.
13. **Desktop chrome never covers itself.** Both maps share one toolbar, placed by `observeDesktopControlRail` (`app/desktop-sidebar-state.ts`): centered over the whole map, moved only to clear an open sidebar and the right-hand buttons, dropping its captions, then the right-hand captions, before taking a second row. The desktop legend keeps its designed size on large windows and shrinks on small ones (`styles/map/map-legends.css`). The default camera framing itself is unchanged. Regression coverage: `tests/desktop-control-rail-placement.test.mjs` and the small-laptop baselines in `tests/smoke/visual-baselines.spec.ts`.
14. **Line alerts are tubes over the line.** Alert rails are opaque and wider than the line they cover: TTC 96 units on its 80-unit lines, GO/UP 196 on its 175-unit corridors. Neither has an outline at rest; only hover and group previews draw one. Tubes have no casing, so where TTC lines run edge to edge (Lines 1 and 2 at St George) neighbouring tubes meet without a gap.

## Working rules

- Orchestration lives in the engine, so a change there reaches both maps. A difference between maps belongs in the map's manifest, definition or content adapter, never in a branch in the engine.
- Verify a change in both modes: pan, release, hover, wheel zoom, toggle reduced motion, and let a refresh pass. Overlays must not blink or restart. TTC often has no active impacts, so compare against a TTC fixture or scenario that has overlays.
- Parity suite: `tests/smoke/map-parity.spec.ts` runs every case on both maps (desktop and mobile Chromium) and expects the same outcome: line-alert hover and press, station hover, name lift, press, keyboard and tap, overlap badges and the chooser (pointer, keyboard, tap), wheel zoom about the pointer and its inverse, trackpad pinch, drag, momentum and a press during a glide, reduced motion, and commute previews. Add a case there, not to a per-map spec, for any shared interaction; a case that passes on one map only is a parity bug.
- Regression coverage: `tests/map-geometry-data.test.mjs` (prepared geometry matches its SVG; station-name boxes), `tests/regional-map-geometry.test.mjs` (GO/UP corridors, train markers, name boxes and badge anchors on the real prepared map), `tests/overlap-badge-layout.test.mjs` (the shared badge layout), `tests/map-motion-parity.test.mjs` (glyphs rest along their lane), `tests/station-alert-model.test.mjs` (station-alert colours, arrows and reach), `tests/map-overlay-obstacles.test.mjs` (badge and connector clearances from the shared sizes), `tests/map-station-artwork.test.mjs` (station targets, hover and selection sizes from each map's artwork, Spadina's two dots, placement by data), the GO/UP plane inventory in `tests/smoke/browser-compat.spec.ts`, `tests/regional-map-content.test.mjs` (poll-only changes do not rebuild), the "regional overlay reconciliation" case in `tests/smoke/dashboard.spec.ts` (dropping and restoring one GO/UP alert leaves the others mounted), the label-hiding and glow-transition assertions in `tests/map-raster-renderer.test.mjs` and `tests/regional-network.test.mjs`, and `tests/map-chooser-follow.test.mjs` plus the settled-camera cases in `tests/overlap-chooser-placement.test.mjs` (chooser follow and sticky placement).
- To compare the two renderers, count GPU layers (DevTools → Layers, or CDP `LayerTree`) and pan paint time on both maps. Give TTC overlays first, for example from the smoke API stub (`tests/smoke/api-stub.mjs`).

- The map shares Chrome's tile memory budget with the whole page. When it is exceeded, Chrome logs `tile memory limits exceeded` and drops tiles page-wide, so the map and sidebar flicker and tear.
- The GO/UP-only tearing after a pan came from camera easing during the drag. Each move eased the stage over 0.1s, so the stage stayed in a transform transition for the whole drag. The redraw when it settled after release overflowed that budget on GO/UP's heavier stage. Direct drags now set the stage transition to `none` in both maps (`startGestureInteraction`, regional `onPointerDown`). Reduced motion hid the bug because it already turns that easing off. Sidebar incident borders were ruled out; they keep a live canvas only while animating.
- The GO/UP-only flicker while zooming with the alert chooser open came from the chooser's group outline. It is two SVG masks around the previewed alerts, and at Union those alerts span whole corridors. Chromium re-rasters masked content at every new scale. At 2560 px wide that overflowed tile memory on every zoom step: about 1,000 `tile memory limits exceeded` warnings in a 5-second burst, against about 60 with the outline hidden. Shrinking the mask region did not help (about 570). TTC's outlines usually cover a short stretch. Masked outlines therefore hide in both maps while the map changes scale. The remaining tile overflow, shared by both maps, came from Chromium re-rastering every stage plane at each zoom step. On desktop the stage gets `will-change: transform` while the scale changes (zoom or camera flight), so Chromium scales the existing raster and re-rasters once when the zoom settles. With both changes, a fast 5-second zoom burst at 2560 px went from about 1,230 warnings to about 65 on GO/UP with the chooser open, and from about 58 to 45 on TTC, with no visible flicker. Mobile performance mode keeps the stage flat. GO/UP hover copies also show and hide without an opacity fade: a fading SVG element gets its own GPU layer sized in GO/UP's SVG units (17038 × 9033 versus TTC's 4500 × 2182).
- `npm --prefix frontend run test:map-zoom-memory` guards this on a real GPU. It spreads two overlapping GO/UP alerts across every corridor and fails above 100 warnings per burst (0 on both maps; about 1,800 before the earlier fixes). Glyph lanes have no clip: every glyph is centred on its alert's path and fits inside the tube's half-width. They were once clipped by a mask as long as the alert; on GO/UP a whole-line delay's mask spanned a corridor, re-rastered at every zoom step (about 160 warnings per burst on live data, page flicker) and held most of GO/UP's drawing-layer area at rest, so it went in plan 09 phase 2. To find a new tile-memory cause, launch Chrome with `--enable-logging=stderr --remote-debugging-port=9222`, reproduce at the user's window size, and switch suspects off with injected CSS over CDP while counting `tile memory limits exceeded` lines per burst. Headless runs at 1440 px did not reproduce this.

## MapLibre System Map (tried and retired)

In October 2026 both System Maps briefly drew with MapLibre from raster tile pyramids, then returned to these SVG renderers: on phones MapLibre's pan and pinch felt worse than the SVG stage's compositor transforms, tiles softened then sharpened while zooming, and first loads were slower. Its reason for existing, desktop zoom flicker at 2560 px, was already fixed here (masked outlines hidden and `will-change` while scaling, above). Keeping both renderers would have doubled every overlay change. Map View still uses MapLibre.

## Known gaps

- Deferred: measure both maps on a low-end Android phone before any renderer change: tap responsiveness (INP), long tasks during a live-data refresh, and GPU layer count during a pinch. Mobile performance is acceptable today, so this waits until a change needs it.
