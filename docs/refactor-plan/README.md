# Application refactor plan

Prepared 2026-09-24 against `ba7939bf84311f3aba4f192aa0bff24b46e2a39a`.
Status: planning complete; implementation and runtime baselines have not started.
Implementer: Gemini 3.8 Flash, working sequentially with review between chunks.

## Agreed scope

Preserve features, appearance, public API contracts, installed user data, and
source/freshness semantics. Remove demonstrably unused code. Recommend larger
restructuring only where it reduces actual maintenance complexity. Feature
removals and behavior corrections require a distinct decision from extraction.
Include all frontend TypeScript, backend Java, schematic and geographic maps,
asset tooling, CSS, tests, supporting scripts, and publication readiness.

Optimize first for finding and changing the owner of a behavior. Runtime
improvements need before/after measurements. There is no line-count target,
framework migration, dependency upgrade campaign, or requirement to rewrite
every file. Existing installations are compatibility targets; no external API
consumers were identified in the interview, so existing contracts remain intact.

## Findings and confidence

Read-only inspection found concrete duplication in regional SVG loading and
backend push candidate routing, mixed responsibilities in dashboard assembly
and frontend session/navigation code, and tests coupled to obsolete source
structure. These are stronger reasons to refactor than file length.

The regional GTFS importer accumulates all departures before batched writes.
That conflicts with the documented bounded-memory requirement; an actual
out-of-memory failure has **not** been observed. Treat its repair as a separate
persistence checkpoint. Likewise, overlapping station reads are a race
candidate to reproduce before changing behavior.

Approximate source inventory, including comments and blank lines: 388 Java
production files / 45,197 lines; 248 frontend TS/TSX files / 77,991 lines; 52
authored style files / 40,654 lines. Generated catalogs and fixture data account
for some size. This was a targeted architecture audit, not a proof that every
unused export, defect, or publication issue has been found.

dependencies: B1 before B2; B4 before B5's shared evaluation; F2 before F3/F6;
M1 before M3's asset extraction; F4 before M5's shell-layout changes;
M2/F7 before deleting their CSS; C1 before CSS
metrics claims. Run V1's applicable baseline before every first workstream
change and V2's affected checks as each workstream stabilizes.

T1–T5 follows the completed application/CSS chunks and precedes final P4/V2
sign-off. Continue migrating affected tests within each implementation chunk;
the final suite pass consolidates the result rather than deferring regression
protection until the end. Re-audit the resulting code, not the original file
layout, when choosing test owners and removing transitional coverage.
Then complete P3a's review of every `AGENTS.md` against the final code and
test commands before P4/V2 sign-off.

## Session contract for Gemini

1. Read this index, the selected chunk, and its scoped guide. Record the current
   commit and working-tree changes. Recheck evidence and callers against HEAD.
2. State the behavior being preserved, files owned by the chunk, and the
   smallest check that can distinguish a correct result from a broken one.
3. Capture missing behavioral coverage at the interface. Replace affected
   source-location assertions in the same chunk. Retain genuine architecture,
   security, asset-ID, and cascade contracts.
4. Make the extraction or consolidation, update all callers, and remove the old
   implementation. If a temporary facade is essential, record its consumer and
   the chunk that removes it. A move with unchanged distributed responsibility
   is not complete.
5. Run focused checks while editing and the required affected-layer gates once
   stable, following [verification](01-verification.md). Review visual diffs
   before accepting snapshots. Record pre-existing failures separately.
6. Update the handoff below with exact checks/results and remaining uncertainty.
   Provide a concrete diff for review before proceeding to the next chunk.

Keep DTO fields, storage keys/version rules, Flyway history, SVG IDs, and CSS
class contracts stable unless the selected chunk explicitly accounts for them.
Revalidate current production wiring before removing an old compatibility path.
Never delete a fallback because the happy path usually succeeds.

If a suspected defect is reproduced, record its trigger and expected behavior
as a separate corrective change. If the fix changes a public contract, feature,
notification outcome, appearance, or persisted format, return that specific
tradeoff to the owner. Routine extraction does not need renewed permission.
